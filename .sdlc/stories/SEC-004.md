## Requirements
- **Functional**: Deploy gate'inin (CI/GitHub Actions yeşil olmadan Railway'e deploy engelleniyor mu) gerçekten aktif olup olmadığı tespit edilir ve PDM'e raporlanır.
- **Non-Functional**: Bu bulgunun bir kısmı (Railway proje ayarları, GitHub branch protection kuralları) repo dışıdır — agent'lar bu ayarları OKUYABİLDİĞİ ölçüde (repo içindeki `.github/workflows/*.yml` dosyaları, varsa Railway config dosyaları) tespit eder; repo dışı/hesap paneli ayarlarını değiştiremez, sadece "şu an X görünüyor, panelden teyit edilmeli" şeklinde raporlar.
- **Business Rules**: Testleri geçmeyen bir commit production'a deploy edilmemeli.
- **Assumptions**: ASSUMPTION — mevcut `dd1d2c6` ve `64d7174` commit'leriyle eklenen GitHub Actions build+test workflow'u (bkz. `git log`) CI'ı çalıştırıyor, ancak bunun Railway deploy'unu GERÇEKTEN engelleyip engellemediği (örn. Railway'in GitHub Checks entegrasyonu, ya da ayrı bir deploy job'ının CI job'ına bağımlı olup olmadığı) doğrulanmamış — bu story'nin asıl amacı bu varsayımı doğrulamak.
- **Constraints**: DevOps veya security bu story kapsamında Railway/GitHub panel ayarlarını DEĞİŞTİRMEZ — sadece mevcut durumu tespit edip raporlar. Değişiklik gerekiyorsa, bu kullanıcının onayıyla ayrı bir adımda yapılır.
- **Dependencies**: Yok.
- **Risks**: Repo içi workflow dosyası "yeşil" görünse bile, Railway tarafında bu workflow'a bağlı bir gate kurulmamışsa (örn. Railway kendi otomatik deploy'unu push anında, CI sonucunu beklemeden tetikliyorsa), CI'ın varlığı yanıltıcı bir güvenlik hissi verir — bu story tam olarak bu boşluğu ortaya çıkarmayı hedefliyor.

## Kullanıcı Değeri
Proje sahibi olarak, "CI yeşil değilse deploy olmaz" güvencesinin gerçekten var olup olmadığını bilmek istiyorum, çünkü bunun sadece varsayılmış olması (gerçekte kurulmamış olması) testleri geçmeyen kodun sessizce production'a çıkmasına yol açabilir.

## Kabul Kriterleri

  Diyelim ki `.github/workflows/` altında build+test workflow'u var (bkz. commit `dd1d2c6`)
  Eğer devops bu dosyayı okursa
  O zaman workflow'un hangi event'lerde (push, pull_request) ve hangi branch'lerde tetiklendiği raporlanır

Senaryo: Sonuç net bir öneriyle raporlanır
  Diyelim ki tespit tamamlandı
  Eğer gate'in aktif olup olmadığı repo içi kanıtla kesin olarak belirlenemiyorsa

## Hata Senaryoları
Senaryo: Workflow dosyası var ama sadece `push` tetikliyor, `pull_request` değil
  Diyelim ki CI yalnızca main'e push'ta çalışıyor
  Eğer bir feature branch'ten gelen kod CI'dan geçmeden main'e merge edilebiliyorsa
  O zaman bu bir bulgu olarak raporlanır — "CI var ama merge öncesi zorunlu değil" ayrımı net yapılır

Senaryo: CI workflow'u var ama test adımı başarısız olduğunda pipeline yeşil kalıyor
  Diyelim ki workflow dosyasında bir adım `continue-on-error: true` veya benzeri bir bayrakla işaretlenmiş
  Eğer bu bulunursa
  O zaman bu Blocker'a yakın bir bulgu olarak raporlanır — "CI'nin varlığı, testin gerçekten gate olduğu anlamına gelmiyor"

Senaryo: Railway ayarlarına repo içinden erişilemiyor
  Diyelim ki Railway deploy tetikleme mantığı tamamen panel içinde, repoda hiçbir iz yok
  Eğer devops bunu tespit ederse
  O zaman "bu bilgi repo içinden doğrulanamaz" diye açıkça, tahmin yürütmeden raporlanır

## Çıktı

### Kapsam teyidi
Bu tespit hem repo içi dosyalar (`.github/workflows/backend-ci.yml`, `backend/nixpacks.toml`) hem de `gh api` ile **salt-okunur** GitHub REST API sorguları (branch protection, rulesets, environments, commit statuses, deployment statuses) üzerinden yapıldı — hiçbir ayar değiştirilmedi, `gh api` sadece GET istekleri için kullanıldı.

### Bulgu 1: CI var, ama deploy'u GATE ETMİYOR — iki bağımsız/paralel sistem
- `.github/workflows/backend-ci.yml`: `push`/`pull_request` (main) tetikleyicili, gerçek bir Postgres servisiyle `./gradlew build` çalıştıran sağlam bir CI workflow'u var. `continue-on-error` gibi bir bayrak yok — test gerçekten başarısız olursa job kırmızı olur.
- **Ama Railway'in deploy tetikleme mekanizması bu workflow'dan tamamen bağımsız.** Railway, GitHub'a kendi commit status'unu (`context: "fisbu - Fisbu"`) doğrudan postluyor ve deploy'u push event'i geldiğinde KENDİSİ başlatıyor — GitHub Actions'ın "build-and-test" check-run'ının sonucunu beklemiyor/sormuyor.
- Kanıt: `gh api repos/CrnBilg/Fisbu/branches/main/protection` → **404** (main branch'inde HİÇBİR branch protection kuralı yok). `gh api repos/CrnBilg/Fisbu/rulesets` → **`[]`** (yeni GitHub Rules API'sinde de hiçbir ruleset yok). Yani "PR'lar CI geçmeden main'e merge edilemez" kuralı da yok — bırakın deploy'u, merge bile CI'a bağlı değil.
- Kanıt 2: `fisbu / production` adlı GitHub Environment'ın (`gh api repos/CrnBilg/Fisbu/environments`) `protection_rules: []` ve `deployment_branch_policy: null` — bu ortamda da Railway'in deploy'unu kısıtlayan hiçbir GitHub-seviyeli kural yok.

**Sonuç: CI yeşil olmasa da (hatta hiç çalışmasa da) Railway deploy'u engellenmiyor.** CI'ın varlığı bir güvenlik hissi veriyor ama gerçek bir gate değil.

### Bulgu 2 (yan bulgu, bu taramada tesadüfen ortaya çıktı): Production şu an "failure" gösteriyor
`gh api repos/CrnBilg/Fisbu/deployments/<son-deployment-id>/statuses` sorgusunda, en son (commit `64d7174`, "ci: setup-java'yı v5'e güncelle") deployment'ın durum geçmişi:
```
2026-08-18T14:39:53Z  success   (ilk deploy, ağustos)
2026-09-10T07:29:51Z  in_progress   (bugün tetiklenen YENİ bir deploy denemesi)
2026-09-10T07:31:33Z  success
2026-09-10T07:31:38Z  success
2026-09-10T07:32:34Z  failure   ← EN GÜNCEL DURUM
```
Bugün (2026-09-10) saat 07:29-07:32 arasında bu commit için yeni bir deploy denemesi olmuş ve **başarısız** ile sonuçlanmış. Bu, SEC-002 üzerinde çalışırken (aynı gün) tesadüfen fark edildi — SEC-004'ün kendi kapsamı dışında ama gözden kaçırılmaması gereken bir operasyonel sinyal.

## Önerilen aksiyonlar (kullanıcı kararı — agent uygulamadı, HITL kuralı)
1. **Branch protection ekleyin** (`main`): GitHub → Settings → Branches → "Backend CI / build-and-test" check'ini "required status check" olarak işaretleyin. Bu, en azından PR merge'lerini CI'a bağlar.
2. **Railway'in deploy tetikleyicisini gözden geçirin**: Railway dashboard → Service → Settings → "Deploy Triggers" — Railway'in "Wait for CI" veya "GitHub Check" bekleme seçeneği olup olmadığını kontrol edin (bazı Railway planlarında/entegrasyon modlarında bu ayarlanabilir).
3. **Bugünkü "failure" deploy'unu inceleyin**: Railway dashboard'daki ilgili deploy log'una (statuses çıktısındaki `target_url` linkinden) bakıp neden başarısız olduğunu görün — bu SEC-002'deki datasource/pooler değişiklikleriyle ilgili olabilir de olmayabilir de, ayrı bir inceleme gerektirir.
